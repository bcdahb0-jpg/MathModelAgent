## 修复：DeepSeek 思考模式 400「reasoning_text must be passed back to the API」

- **现象**：任务 20260913-101444，Coder 第 2 轮请求起持续 400（`第12~22次重试` 刷屏），一次 400 被无限重试。
- **环境**：Coder 配 `api_type=openai-responses`、`model=deepseek-v4-flash`、`base_url=https://api.deepseek.com/v1`
  （走 DeepSeek 官方 `/responses`，见 09-10 日志里的请求体 dump 记录）。
- **根因（两端都错）**：
  1. DeepSeek 响应里思维链在 `reasoning item.content = [{type:"reasoning_text", text}]`；openai SDK 1.75 的
     `ResponseReasoningItem` 只有 `id/summary/type/status`，`content` 靠 `extra="allow"` 透传成**原始 list**。
     旧 `_extract_reasoning_text` 只认 `reasoning_text`/str 型 content/summary → 返回空 → 历史从不存 CoT →
     带 `tools` 的下一轮被服务端判定「思维链没回传」→ 400（不带 tools 的 Agent 不受影响）。
  2. 旧回传格式 `{"type":"reasoning","reasoning_text":<str>}` 不是规范形态，即使取到了也等于没传；
     规范要求 `content: [{type:"reasoning_text", text}]`。
- **修复**：
  - `openai_responses.py`：重写 `_extract_reasoning_text`，新增 `_collect_text`（兼容 dict / SDK 对象 / 纯字符串
    内容块）；回传改 `_to_reasoning_blocks` → `{"type":"reasoning","content":[{...}]}`；顺序保持
    reasoning → assistant 文本 → function_call → function_call_output。
  - `llm.py`：4xx（除 429）**快速失败不再重试**（旧代码 max_retries=None → 4xx 无限循环刷日志）；
    `time.sleep` → `await asyncio.sleep`（否则重试等待阻塞事件循环，停止按钮失效）。
- **验证**：离线单测 4 种 reasoning 形态提取 + `_messages_to_input` 顺序全部 PASS。**需重启后端生效。**
- **注意**：修复写在**未提交**的工作区改动里（`git status` 显示 2 个 M），stash@{0} 里也存在对同一文件的
  类似改动，若再次 `git restore --source=stash@{0}` 会覆盖本次修复，建议先 commit。

## 修复：参考文献整章为空（真实根因 = 提示词与正则的格式不一致）

- **上一条诊断的修正**：`writer_agent.py` 的 `footnotes` 字段确实是死代码（`UserOutput.set_res` 存了但
  `get_result_to_save` 从不读它），**但它不是参考文献为空的原因**。真正的引用链路是：提示词要求模型在正文里
  写行内标记，`UserOutput.replace_references_with_uuid` 把这些标记抽成 `self.footnotes`，最后
  `append_footnotes_to_text` 生成「## 参考文献」列表。
- **真实根因（实证）**：提示词写的是 `{[^1] 完整引用信息}`（**无冒号**），而
  `replace_references_with_uuid` 的正则 `\{\[\^(\d+)\]:\s*(.*?)\}` **要求冒号** → 一条都匹配不上 →
  `footnotes` 恒为空 → 「参考文献」只剩空标题。
  证据：本次任务 `res.json` 里模型完全照提示词输出了 `{[^1] Gang Wang, ...}`、`{[^2] ...}` 共 6 处，
  全部无冒号。
- **修复**：
  - `app/models/user_output.py`：新增类常量 `REFERENCE_PATTERN = r"\{\[\^(\d+)\]\s*:?\s*(.*?)\}"`
    （`:` 可选），`replace_references_with_uuid` 改为 `re.sub` + 回调，一次完成“去重复用 UUID / 新建 UUID”，
    顺带修掉旧实现 findall+两次 re.sub 里的同一处冒号硬编码。
  - `app/core/prompts/writer.py`：引用格式改为 `{[^1]: 完整引用信息}` 并注明「`[^1]` 后必须紧跟英文冒号」。
  - 新增 `app/tests/test_user_output.py`（4 个用例：带冒号 / 不带冒号 / 重复引用复用 UUID / 文末生成参考文献）。
- **验证**：用本次任务真实的 `res.json` 跑 `get_result_to_save()` → 生成 6 条编号参考文献，正文 6 处
  `[^n]` 正常，无残留 `{[^` 标记；4 个新用例全过。（`pytest` 未装，用 `python -m unittest` 跑。）
- **顺带发现（与本次改动无关）**：`app/tests/test_common_utils.py::test_split_footnotes` 本来就失败 ——
  `split_footnotes` 只删脚注定义块，不删正文里的 `[^n]` 内联标记，而用例期望删掉。未处理，待定。

## 修复（第二轮）：docx 里看不到参考文献 —— `[^n]` 被 pandoc 当成了脚注

- **用户反馈**：改完引用解析后重跑（任务 20260913-105359-5f896c6d），仍说「还是没有参考文献」。
- **实测**：`res.json` 里有 3 处 `{[^n]: ...}` 标记，`res.md` 末尾**确实有**参考文献定义，
  说明第一轮修复已生效 —— 问题出在**呈现层**。
- **真实根因**：`append_footnotes_to_text` 输出的是 markdown 脚注定义 `[^n]: 内容`，
  `sort_text_with_footnotes` 输出的正文内联标记也是 `[^n]`。pandoc 会把它们识别为**脚注** →
  转 docx 时文献正文被搬进 `word/footnotes.xml`（Word 页脚注释），`word/document.xml` 里
  「参考文献」标题下面**一个段落都没有**。用户看到的正是这个空标题
  （现场还有 Word 占用 `~$res.docx` 锁定文件）。
- **修复**（`app/models/user_output.py`）：
  - `sort_text_with_footnotes`：正文内联标记 `[^{n}]` → `[{n}]`；并用 `dict.fromkeys` 去重、
    只在首次分配编号时递增（原来同一 uid 出现两次会占用两个编号，导致正文编号与文末列表对不上）。
  - `append_footnotes_to_text`：改为 `## 参考文献` + 每条 `[{n}] {content}`，**条目之间空行分隔**
    （pandoc 会把相邻行并成一段，必须空行才能一条一段）；无引用时不再留空标题，改为打 WARNING。
  - 新增依赖：`from app.utils.log_util import logger`。
  - 测试同步更新（断言 `[1] 张三...` / 正文 `摘要[1]` / 不含 `[^` / 无引用不出标题），5 个用例全过。
- **验证**：用 20260913-105359 的 `res.json` 重建 → 正文 `[1][2][3]` 内联、文末 `## 参考文献` + 三条
  `[n] ...`；重新 pandoc 转 docx 后 `word/footnotes.xml` **已无文献内容**，`document.xml` 里标题下直接
  跟着三条文献。注意：原 `res.docx` 被 Word 占用写不进去，新文件另存为
  `project/work_dir/20260913-105359-5f896c6d/res_含参考文献.docx`；原文件备份在
  `%TEMP%\mmagent_bak_20260913-105359-5f896c6d\`。
- **教训**：这个项目最终论文是 md → pandoc → docx，凡是写进 md 的标记都要考虑 **pandoc 的语法解释**；
  `[^n]` 是脚注语法，想显示成正文列表就得用 `[n]`。
